# 🕵️ RingTrace — Fraud-Ring Detective Agent

**An agent that investigates by walking a graph, not by guessing from a prompt.**

Built for **WeMakeDevs × FalkorDB Graph Hacks 2026 — Track 01: "Agents That Act on Connected Data."**

![RingTrace architecture](docs/architecture_diagram.png)

> ⚠️ **All data in this project is 100% synthetic**, generated by
> `ingestion/generate_synthetic_data.py` specifically for this demo. No real
> people, accounts, devices, IPs, or transactions are represented, and no
> real financial system is ever contacted — every "action" (flagging,
> escalation, watchlisting…) is simulated and only writes to the demo graph.

---

## 1. The problem

Fraud rings don't look suspicious one row at a time. A single account, a
single transaction, a single login — in isolation, none of it looks wrong.
What gives a ring away is **structure**: five accounts sharing one device,
money hopping through four intermediaries before landing on one collector
account, a cluster of "unrelated" wallets all logging in from the same IP.

That structure lives naturally in a **graph**. Flattening it into rows for a
classifier (or a prompt for an LLM) throws away exactly the signal that
matters.

## 2. The solution

RingTrace is an investigation agent that:

1. Loads an account/transaction/identity graph into **FalkorDB**.
2. Lets an agent (LLM-driven, or a deterministic rule-based planner when no
   LLM key is configured) **dynamically call graph tools** — find the
   connected component, rank likely ring leaders by PageRank, trace the
   money, check for shared devices/IPs — **reading each result before
   deciding what to check next**, exactly like a human fraud investigator
   would.
3. Turns the accumulated graph evidence into an **explainable ML risk
   score**, then a transparent, rule-based **verdict + recommended action**.
4. Lets the investigator **execute (simulated) actions** — escalate, flag,
   add to watchlist — that write real audit nodes back into the graph.

**The test we built against:** *"Without the graph, this agent could not
have made this decision."* Every verdict RingTrace reaches cites specific
graph paths, specific shared identifiers, specific PageRank results — not a
generic LLM opinion.

## 3. Why graphs, why FalkorDB

Fraud rings *are* graphs: `Account —TRANSFERRED_TO→ Account`,
`Account —USES_DEVICE→ Device ←USES_DEVICE— Account`. Two graph primitives do
most of the real work here:

- **Weakly Connected Components (WCC)** instantly isolates "who is in this
  ring with me" — the alternative (self-joins / recursive SQL CTEs) gets
  ugly and slow fast.
- **PageRank** over the money-flow graph identifies the *ringleader* — the
  account that disproportionately collects funds — with zero hand-tuned
  heuristics.

FalkorDB was chosen because it's a **property graph with those algorithms
built in** (`CALL algo.WCC(...)`, `CALL algo.pageRank(...)`) and speaks
**Cypher** over a **Redis-compatible wire protocol**, so the whole stack
(graph + "cache" + pub/sub if needed later) is one lightweight service — a
good fit for a hackathon MVP that still "looks production-capable."

**Crucially: FalkorDB is not a reporting/visualization layer bolted on
after the fact.** Every tool the agent calls (`find_fraud_ring`,
`rank_ring_leaders`, `trace_money_path`, `find_identity_links`,
`calculate_risk_score`) issues real Cypher/algo calls against FalkorDB, and
the **structured results of those calls are what the decision engine reads**
to pick a verdict (see `agent/decision.py`). Change the graph — remove a
shared device, delete a money edge — and the verdict changes. That's
demonstrated explicitly in [Section 11](#11-the-demo-3-cases-that-prove-the-graph-drives-the-decision).

## 4. Architecture

```
┌──────────────┐   Cypher / algo.*   ┌───────────────────────────────┐
│   FalkorDB   │◄───────────────────►│   tools/  (MCP-style layer)   │
│ (graph store │                     │  7 required + 4 optional      │
│  + WCC/PageRank)                   │  tools, typed I/O, validation │
└──────────────┘                     └───────────────┬───────────────┘
                                                       │ ToolResult
                                      ┌────────────────▼───────────────┐
                                      │   agent/   (reasoning loop)    │
                                      │ LLM tool-calling  OR           │
                                      │ deterministic rule-based       │
                                      │ planner (agent/rule_based.py)  │
                                      └────────────────┬───────────────┘
                                                        │ evidence_trail
                                      ┌─────────────────▼──────────────┐
                                      │ agent/decision.py                │
                                      │ transparent rules -> verdict,    │
                                      │ confidence, recommended_action   │
                                      └─────────────────┬──────────────┘
                                                         │
                 ┌───────────────────────────────────────▼─────────────┐
                 │ app/dashboard.py (Streamlit) — sections A-G          │
                 │ tools/actions.py — simulated case/flag/escalate/     │
                 │ watchlist actions, written back into FalkorDB        │
                 └───────────────────────────────────────────────────────┘
```

Models (`models/`) compute graph-derived features (degree, PageRank,
component size, shared-identifier counts, hop-distance to known alerts…)
and feed a RandomForest classifier; `models/risk_scorer.py` additionally
applies a **graph-evidence guardrail** (Section 9) on top of the raw model
score so the final number always stays grounded in what the graph actually
shows.

## 5. Graph schema

**Node labels:** `Person`, `Account`, `Device`, `IP`, `Transaction`,
`Broker`, `Merchant`, `Alert`, plus agent-written `Case` and
`WatchlistEntry` nodes.

**Relationships:**

| Relationship | Direction | Meaning |
|---|---|---|
| `OWNS` | Person → Account | Account ownership |
| `USED_DEVICE` | Person → Device | Device used by a person |
| `USES_DEVICE` | Account → Device | Device used to access an account |
| `LOGGED_FROM` | Person/Account → IP | Login/session IP |
| `TRANSFERRED_TO` | Account → Account | Denormalized money-flow edge (drives PageRank) |
| `ROUTED_THROUGH` | Account/Transaction → Broker | Funds routed through a broker/mixer |
| `FROM` / `TO` | Transaction → Account | Transaction endpoints |
| `TO_MERCHANT` | Transaction → Merchant | Merchant-bound payment |
| `FLAGS` | Alert → Account | Existing rules-engine alert |
| `LINKED_TO` | Account → Account | **Materialized identity-resolution edge** — derived at load time from shared device / IP / owning person / broker / direct transfer. This is what makes `algo.WCC` directly usable for ring detection. |
| `INVESTIGATES` | Case → Account | Agent-created case record |
| `WATCHES` | WatchlistEntry → entity | Agent-created watchlist entry |

Indexes are created on every `.id` property plus a few hot filter fields
(see `graph/schema.py`) so lookups stay O(log n) as the graph grows.

## 6. The agent's tool layer (`tools/`)

Every tool is a `ToolSpec`: a name, an LLM-facing description (**explaining
WHEN to call it**, not just what it does), a Pydantic input model (typed,
validated), and a handler that **always returns a `ToolResult`** —
tools never raise; failures become `{ok: False, error: "..."}` so the agent
loop degrades gracefully instead of crashing.

### Investigation tools (read-only, pure graph queries)

| Tool | Graph operation | When the agent should call it |
|---|---|---|
| `get_account_context` | 1-hop neighborhood fetch | Always first — establishes what we know about the target. |
| `find_fraud_ring` | `algo.WCC` over `LINKED_TO` | To check whether the account belongs to a larger connected structure. |
| `rank_ring_leaders` | `algo.pageRank` over `TRANSFERRED_TO` | Once a ring is found, to identify the likely leader/mule. |
| `trace_money_path` | Variable-length shortest-path over `TRANSFERRED_TO` | To see exactly how money moves between the account and a suspicious endpoint. |
| `find_identity_links` | Shared-device/IP/person/broker lookups | To explain *why* accounts are connected (confirms the ring isn't coincidental). |
| `calculate_risk_score` | Graph feature extraction + RandomForest + guardrail | To get an explainable, numeric severity for a verdict. |
| `generate_verdict` | Synthesizes the evidence trail | Final step — call once sufficient evidence has been gathered. |
| `timeline_analysis` *(optional)* | Chronological transaction ordering | To spot bursty/velocity patterns. |
| `broker_analysis` *(optional)* | Broker/mixer fan-in analysis | When a broker shows up in a money path. |
| `compare_accounts` *(optional)* | Side-by-side feature diff | To contrast a suspicious account against a clean one. |
| `investigate_entity` *(optional)* | Generalized entity lookup (device/IP/person) | When the query starts from a non-account entity. |
| `generate_case_report` *(optional)* | Builds the Markdown report | For display/export without necessarily ending the investigation. |

### Action tools (simulated, graph-mutating)

| Tool | What it writes |
|---|---|
| `create_investigation_case` | A `Case` node linked to the account via `INVESTIGATES` |
| `flag_account` | `Account.flagged = true` + reason |
| `mark_high_risk` | `Account.risk_level = 'HIGH'`, `status = 'UNDER_REVIEW'` |
| `request_manual_review` | `Account.status = 'MANUAL_REVIEW_REQUESTED'` |
| `escalate_case` | `Case.status = 'ESCALATED'` |
| `add_to_watchlist` | A `WatchlistEntry` node `WATCHES` any entity (account/device/IP/person/broker) |
| `export_case_summary` | Writes a Markdown report to `reports/` |

Every action tool call is itself appended to the evidence trail, so the
final case report shows not just *what was found* but *what was done about
it*.

## 7. The reasoning loop (`agent/`)

```
understand target → get_account_context
        │
        ▼
   is it in a ring?  ──no──► skip ring tools, still check identity links
        │ yes
        ▼
  rank_ring_leaders  → identify leader
        │
        ▼
  trace_money_path(account → leader)  → confirm the flow
        │
        ▼
  find_identity_links  → confirm WHY these accounts are connected
        │
        ▼
  calculate_risk_score → explainable ML score (+ graph guardrail)
        │
        ▼
  generate_verdict → numbered reasoning, ring/leader/path, confidence, action
```

Two interchangeable planners implement this:

- **LLM mode** (`agent/llm.py` + `Investigator._run_llm_loop`): if
  `LLM_PROVIDER` + `LLM_API_KEY` are set (works with Groq, OpenAI, or any
  OpenAI-compatible endpoint), an LLM with function/tool-calling picks the
  next tool after reading each previous tool's *actual* JSON output — real
  dynamic tool selection, not a canned script.
- **Rule-based mode** (`agent/rule_based.py`, the default — **no API key
  required**): a deterministic planner follows the same methodology but
  skips steps the evidence doesn't justify (e.g. an isolated account never
  triggers `rank_ring_leaders`). The demo is never broken by a missing/rate
  -limited LLM key.

In **both modes**, the actual verdict is produced by
`agent/decision.py::build_verdict`, reading the structured `evidence_trail`
— never by free-form LLM text. This keeps every decision auditable and
exactly reproducible from the graph evidence collected, independent of which
planner ran.

## 8. Explainable ML risk scoring (`models/`)

`models/features.py` computes, per account, purely graph-derived features:
degree & weighted degree on `LINKED_TO`, PageRank on both the identity graph
and the money-flow graph, connected-component size, counts of accounts
sharing a device/IP, transaction count & total amount, net flow, hop-distance
to the nearest known `Alert`, broker count, and the fraction of
directly-linked neighbors that are themselves already flagged
(`suspicious_neighbor_ratio`).

`models/train.py` trains a `RandomForestClassifier` against
`data/processed/ground_truth.csv` — **synthetic ground truth only, used for
training/evaluation, never written onto graph nodes** (the agent cannot
"cheat" by reading a label; it has to infer risk from structure, like a real
investigator). The current run: **205 accounts, 75/25 split, accuracy /
precision / recall / F1 / ROC-AUC all 1.00** — see
`evaluation/synthetic_eval_report.json` for the full report. This reflects
how cleanly the model recovers the *planted* synthetic ring structure; it is
**not a claim about real-world fraud-detection performance**.

### The graph-evidence guardrail

A small RandomForest trained on a few hundred synthetic accounts can be
over-confident at the margins (e.g. an account with exactly one transaction
and no other signal). Rather than overfit the model further, RingTrace adds
a transparent, rule-based **guardrail** (`_graph_evidence_strength` in
`models/risk_scorer.py`) that caps the raw ML score based on what the graph
actually shows:

- **No shared identifiers, no alerts, no ring membership** → capped at 0.20
  (LOW), regardless of what the model predicts.
- **Weak evidence** → capped at 0.55.
- **Identity linkage confirmed (shared device/IP, ring membership) but no
  confirmed money trail and no nearby alert** → capped at 0.72 (HIGH, not
  CRITICAL) — this is the line between "looks related" and "is laundering
  money."
- **Strong evidence** (ring + money trail + alert proximity) → the raw model
  score passes through untouched.

The dashboard's Risk panel shows both `raw_model_score` and the final
graph-adjusted `risk_score` whenever the guardrail fires, so the
investigator sees exactly when and why the graph overrode the model.

## 9. Synthetic data generator (`ingestion/generate_synthetic_data.py`)

Fully configurable via env vars / CLI flags: `RING_COUNT`,
`ACCOUNTS_PER_RING`, `LEGIT_PERSON_COUNT`, `NORMAL_TRANSACTION_COUNT`,
`NOISE_LEVEL`, `FRAUD_RATIO`, `RANDOM_SEED`.

It plants a **fixed, hand-authored demo scenario** (the exact narrative used
in the killer demo below) plus a configurable population of:

- Legitimate background accounts & transactions (including dormant accounts
  and benign transaction "circles," so WCC doesn't accidentally merge
  everything into one giant component).
- Additional fraud rings cycling through **5 named patterns**:
  `dense_ring`, `shared_device_ring`, `shared_ip_cluster`,
  `layered_movement`, `central_mule_leader`.

Ground truth is written **only** to `data/processed/ground_truth.csv` for
evaluation — never onto graph nodes.

## 11. The demo: 3 cases that prove the graph drives the decision

Run each of these from the dashboard's quick-preset dropdown (or
`inv.investigate(account_id=...)` directly):

| Case | Account | Graph evidence | Risk class | Verdict / action |
|---|---|---|---|---|
| **A — isolated** | `A1100` | 1 other linked account, no shared devices/IPs, no alerts | **LOW** | `NO_ACTION_REQUIRED` |
| **B — identity-linked only** | `A1200` | 5-account component, 4 accounts share an IP, **no confirmed money trail to a known-bad entity** | **HIGH** | `FLAG_AND_REQUEST_MANUAL_REVIEW` |
| **C — ring + money flow** | `A1027` | 9-account component, shares a device with 7 accounts, `A1001` is the PageRank-identified leader, a confirmed 5-hop money trail `A1027→A1023→A1024→A1025→A1026→A1001`, plus a pre-existing rules-engine alert | **CRITICAL** | `ESCALATE_FOR_MANUAL_INVESTIGATION` |

Identical decision logic (`agent/decision.py`) run against three different
graph neighborhoods produces three genuinely different outcomes — this is
asserted directly in `tests/test_decision.py::test_verdicts_differ_across_cases`.

**The scripted 3–5 minute walkthrough:**

1. Investigator opens RingTrace and enters alert `A1027`.
2. Agent calls `get_account_context` → sees the account, its device, its IP.
3. Agent calls `find_fraud_ring` → FalkorDB's `algo.WCC` reveals a 9-account
   connected component.
4. Agent calls `rank_ring_leaders` → FalkorDB's `algo.pageRank` over
   `TRANSFERRED_TO` surfaces `A1001` as the money collector.
5. Agent calls `trace_money_path(A1027 → A1001)` → a clean 5-hop chain.
6. Agent calls `find_identity_links` → confirms the shared device (`D77`,
   7 accounts) and shared IP explain the connections.
7. Agent calls `calculate_risk_score` → 0.98, CRITICAL.
8. Agent calls `generate_verdict` → **"FRAUD RING CONFIRMED" →
   ESCALATE_FOR_MANUAL_INVESTIGATION**, with a numbered reasoning trail.
9. Investigator clicks **Execute recommended action** → a `Case` node is
   created, the account is flagged + marked high-risk + sent to manual
   review, and the case is escalated — all visible immediately as new graph
   writes.
10. Investigator downloads the Markdown case report.

GRAPH → REASONING → DECISION → ACTION, visibly, at every step.

## 12. Dashboard (`app/dashboard.py`, Streamlit)

- **A. Investigation Input** — account/alert ID, quick demo presets, optional
  natural-language instruction.
- **B. Agent Investigation** — live, expandable trace of every tool call
  (inputs, outputs, timing), plus the LLM's narrative when LLM mode is active.
- **C. Graph View** — interactive Pyvis network: the ring, shared
  devices/IPs as distinct node shapes, the traced money path highlighted in
  red with per-edge amounts.
- **D. Risk** — a gauge (raw vs. graph-adjusted score), risk class, and a
  bar chart of top contributing graph features.
- **E. Evidence** — the numbered reasoning trail, money path table, ring
  member list.
- **F. Final Decision** — verdict banner, confidence, recommended action
  description, and an **"Execute recommended action"** button that performs
  the simulated action and shows the resulting graph writes.
- **G. Case Report** — downloadable Markdown report combining everything
  above.

## 13. Setup

### Option A — Docker (recommended, zero native build issues)

```bash
cp .env.example .env     # optionally add an LLM key; works fine without one
docker compose up --build
```

This starts FalkorDB (ports `6379` + the FalkorDB browser UI on `3000`) and
the RingTrace app (port `8501`). On first boot the container automatically
generates the synthetic dataset, loads it into FalkorDB, and trains the risk
model before launching the dashboard.

### Option B — Local Python

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env

./scripts/setup_falkordb_local.sh      # starts FalkorDB via Docker, or see
                                        # the script's fallback instructions
./scripts/run_pipeline.sh              # generate data + load graph + train model

streamlit run app/dashboard.py --server.address 0.0.0.0 --server.port 8501
```

### Environment variables (`.env.example`)

| Variable | Purpose | Default |
|---|---|---|
| `FALKORDB_HOST` / `FALKORDB_PORT` | Where to reach FalkorDB | `localhost:6379` |
| `FALKORDB_GRAPH` | Graph name | `ringtrace` |
| `LLM_PROVIDER` | `none` \| `groq` \| `openai` | `none` (rule-based fallback) |
| `LLM_API_KEY` | API key — **never hardcoded**, read from env only | _(empty)_ |
| `LLM_BASE_URL`, `LLM_MODEL` | OpenAI-compatible endpoint + model | Groq `llama-3.3-70b-versatile` |
| `LLM_TIMEOUT_SECONDS`, `LLM_MAX_TOOL_ITERATIONS` | Guardrails against a hung/looping agent | `20`, `8` |
| `RING_COUNT`, `ACCOUNTS_PER_RING`, `LEGIT_PERSON_COUNT`, `NORMAL_TRANSACTION_COUNT`, `NOISE_LEVEL`, `FRAUD_RATIO`, `RANDOM_SEED` | Synthetic data generator knobs | see `.env.example` |

## 15. Security & reliability notes

- No secrets are hardcoded; all credentials/keys come from environment
  variables (`.env`, excluded from git).
- All Cypher is parameterized (`$param` placeholders) — no string-built
  queries, no injection surface.
- Every tool call is wrapped so exceptions become structured
  `{ok: False, error: ...}` results instead of crashing the agent loop or
  the dashboard.
- `graph.connection.health_check()` is called before every investigation;
  if FalkorDB is unreachable the dashboard shows a clear banner instead of a
  stack trace.
- If no LLM key is configured, or the LLM call fails/times out, RingTrace
  transparently falls back to the deterministic rule-based planner — the
  demo always produces a complete, evidence-backed investigation.
- All demo "actions" are simulated and scoped to the demo graph only; no
  real financial system is ever contacted.

## 16. Performance & scalability notes (design intent, not over-built for the MVP)

| Phase | Scale | Approach |
|---|---|---|
| 0 | 0–10K edges (this demo) | Single FalkorDB instance, in-memory, indexes on `.id` — exactly what's shipped here. |
| 1 | 10K–1M edges | Add indexes on hot filter properties (`status`, `timestamp`), paginate `find_identity_links`/`trace_money_path` result sets, cache `GraphFeatureCache` per investigation session (already implemented in `tools/context.py`). |
| 2 | 1M–100M edges | Partition ingestion into batched `UNWIND` writes (already the pattern used in `ingestion/load_to_falkordb.py`), move WCC/PageRank to scheduled background jobs with materialized `component_id`/`pagerank` properties instead of on-demand `algo.*` calls per request. |
| 3 | 100M+ edges | FalkorDB Cloud / clustered deployment with read replicas, pre-aggregated ring/leader tables refreshed on a cadence, the agent's tools switch from live graph algorithms to reading those pre-aggregated results for latency-sensitive paths. |

The hackathon build intentionally stays at Phase 0 — a single FalkorDB
instance, on-demand `algo.WCC`/`algo.pageRank` calls — because that's what
makes the live "graph → reasoning → decision" chain visible and fast in a
demo, without speculative infrastructure that would never be exercised.

## 17. Limitations

- The RandomForest is trained on a small, synthetic, intentionally
  clean dataset — its 1.00 metrics describe recovering a planted structure,
  not real-world generalization.
- The rule-based decision thresholds (guardrail caps, risk-class cutoffs)
  are hand-tuned for this demo's scenario design, not calibrated against
  real fraud data.
- `find_fraud_ring`'s "ring" threshold (component size ≥ 3) is a simple
  heuristic; real investigations would weigh component *density*, not just
  size.
- No persistence/auth layer for the dashboard itself — it's a single-user
  investigator tool, as scoped for the hackathon.

## 18. Roadmap

- Materialize `component_id` / `pagerank_money` as node properties on a
  schedule, so large-graph investigations don't re-run `algo.*` per request.
- Expand the synthetic generator with adversarial patterns (rings that
  deliberately avoid shared devices/IPs, relying only on timing/velocity).
- Multi-tenant case management + auth for the dashboard.
- Human-in-the-loop feedback loop: investigator overrides feed back into
  model retraining.
